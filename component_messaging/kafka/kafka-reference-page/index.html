Core Concepts

Kafka Anatomy

▸ Topic

Named log

A category of events. Append-only, durable, ordered. Think of it as the API contract between producer and consumer.

▸ Partition

Physical shard

A topic is split into N partitions. Each lives on one broker (leader). Messages within a partition are ordered by offset.

▸ Offset

Immutable position

Every message has an offset — its position in the partition. Offsets only ever increase. Consumer commits offsets to track progress.

▸ Consumer Group

Independent cursor

A named group with its own offset per partition. Multiple groups on the same topic each receive every message independently.

Mental Model

Topic = contract · Partition = parallelism unit · Offset = position · Consumer group = independent reader

Topics & Partitions

How partition routing works

The partition key is hashed to determine which partition a message lands on. Same key always → same partition → ordering guaranteed per key.

Partition 0
off:0http_requests43.5
off:1http_requests88.1
off:2http_requests34.5
Partition 1
off:0error_rate61.7
off:1error_rate90.4
off:2error_rate15.6
Partition 2
off:0p99_latency68.4
off:1cpu_usage8.9
off:2memory_used32.8

Key design rules

  • High-cardinality keys distribute load evenly — user_id, order_id, metric_name
  • Low-cardinality keys create hot partitions — avoid country, status, true/false
  • null key = round-robin across all partitions — no ordering, maximum distribution
  • Partitions can only increase, never decrease — set higher than you think you need
  • Round up to next power of 2 — 16, 32, 64, 128 — simplifies consistent hashing

Retention policies

PolicyConfigUse case
Time-basedlog.retention.hours=168Pipelines — data lives downstream (TSDB, ClickHouse)

Compactioncleanup.policy=compactCDC / state sync — keep latest value per key forever

Producers & Acknowledgements

acks settingDurabilityLatencyUse when
acks=0 none — fire & forget Lowest Metrics where occasional loss is acceptable
acks=1 leader only Medium Moderate durability, leader crash = possible loss
acks=all all ISR replicas Highest Production always — zero data loss
Production Rule

Always pair acks=all with min.insync.replicas=2 on the broker. Together they guarantee a write is on at least 2 replicas before the producer gets confirmation.

Custom partitioner (dedicated partition ranges)

python
# Route each service to its own partition range
PARTITION_MAP = {
    "order-svc":     0,   # P0
    "inventory-svc": 1,   # P1
    "payment-svc":   2,   # P2
}

def custom_partitioner(key_bytes, all_partitions, available):
    service = key_bytes.decode()
    if service in PARTITION_MAP:
        return PARTITION_MAP[service]
    return hash(key_bytes) % len(all_partitions)

producer = KafkaProducer(
    bootstrap_servers=BOOTSTRAP,
    partitioner=custom_partitioner,
    acks=1,
)
Core Concepts

Consumers & Consumer Groups

subscribe() vs assign()

APIBehaviourRebalanceUse when
subscribe(topic) Kafka assigns partitions automatically. Partitions redistributed when consumers join/leave. automatic Standard consumer groups — most use cases
assign([TopicPartition]) You specify exact partitions. No group coordinator. No rebalancing ever. manual Dedicated partition isolation per service

More consumers in same group vs more groups

ActionEffectCeiling
Add consumers to same group Partitions split between them — work is shared. Each message processed once. Max consumers = partition count. Beyond that, extras are idle.
Add a new consumer group New group gets its own independent cursor. Every message flows to every group. No limit on number of groups.

Manual offset commit (always do this)

python
from kafka import KafkaConsumer
from kafka.structs import OffsetAndMetadata

consumer = KafkaConsumer(
    "metrics.raw",
    bootstrap_servers=BOOTSTRAP,
    group_id="rollup-worker",
    auto_offset_reset="earliest",
    enable_auto_commit=False,   # always False in production
)

for tp, msgs in consumer.poll(timeout_ms=1000).items():
    for m in msgs:
        process(m)
    # commit only after successful processing
    consumer.commit({
        tp: OffsetAndMetadata(msgs[-1].offset + 1, None)
    })
Warning — auto-commit

enable_auto_commit=True commits every 5 seconds regardless of whether processing succeeded. A crash mid-batch silently loses messages. Always use manual commit.

Core Concepts

Replication & High-Watermark

Why the high-watermark exists

The LEO (Log End Offset) is the highest offset on the leader's disk. The HWM (High-Watermark) is the highest offset confirmed by all ISR replicas. Consumers can only read up to the HWM.

off:0
✓
off:1
✓
off:2
✓
off:3
✓
off:4
⋯
off:5
⋯
▲ HWM = 3 — consumer reads up to here ▲ LEO = 5 — leader has these, followers don't yet

If Kafka allowed reading off:4 and off:5 and the leader crashed before replication completed, the new leader would only have off:3. The consumer would have processed messages that no longer exist anywhere — data loss.

ISR — In-Sync Replicas

  • Followers that are caught up within replica.lag.time.max.ms (default 30s)
  • Leader drops a follower from ISR if it falls behind — write throughput is not blocked
  • HWM advances as soon as min.insync.replicas confirm — not necessarily all replicas
  • When a broker dies, controller elects the best ISR follower as new leader in ~10–30s

Replication factor guide

RFCan loseUse for
1Nothing — single point of lossLocal dev only
21 brokerNon-critical data
31 broker with zero data lossAll production workloads
Core Concepts

Brokers & Controller

The controller is not a separate process — it is a role held by one of your existing brokers. In KRaft mode (Kafka 3.3+), a Raft quorum among controller-eligible brokers handles election with no ZooKeeper dependency.

Legacy (ZooKeeper)Modern (KRaft)
Controller electionFirst broker to claim ZK ephemeral nodeRaft consensus among quorum voters
Metadata storeZooKeeper@metadata internal topic
Failover time~30–60 secondsMilliseconds
Partition ceiling~200K (ZK bottleneck)Millions
Ops overheadTwo systems to manageSingle system

Three controller responsibilities

  • Leader election — when a broker dies, pick next ISR replica as leader for all affected partitions
  • Partition reassignment — when you add brokers or change partition count, coordinate replica moves
  • Metadata authority — single source of truth for which broker leads which partition

Partition Sizing

formula
P_throughput = ceil( peak_MB/s  ÷  broker_ceiling_MB/s_per_partition )
P_consumer   = ceil( peak_msg/s ÷  msgs_per_consumer_per_s )
P_min        = max( P_throughput, P_consumer )
P_final      = nextPowerOf2( P_min × (1 + headroom%) )
ScaleMsg/sPartitionsConsumers/groupBrokers
small< 10K8–168–163
medium10K–100K32–6432–643–5

very large> 1M512–2048512–204812–30+
Hard Ceiling

Max ~4,000 partitions per broker. Each partition = open file handles + memory for ISR tracking. Beyond 4K per broker, controller election and rebalances slow significantly.

Design Patterns

Failure Modes

FailureWhat happensFix
Consumer lag grows Consumer slower than producer. Offset gap widens. Add consumers up to partition count. Then add partitions.
Crash mid-batch (auto-commit) Offset already advanced. Messages lost silently. Always enable_auto_commit=False. Manual commit after processing.
Rebalance storm Consumers join/leave rapidly. Throughput drops to zero. Tune session.timeout.ms. Use static membership group.instance.id.
Hot partition Bad key choice. One consumer overwhelmed, rest idle. Choose high-cardinality keys. Add random suffix for uniform distribution.
Message too large Default max 1 MB. Rejected by broker. Store payload in S3, publish reference pointer. Or increase message.max.bytes.
Broker leader failure Consumers stall ~10–30s during ISR election. RF≥3, min.insync.replicas=2, acks=all.
microk8s Setup

Deploy Kafka on microk8s

Uses official apache/kafka:3.9.0 image in KRaft combined mode. Two listeners — INTERNAL for pod-to-pod traffic, EXTERNAL exposed via NodePort 30092 for laptop access.

bash — deploy
# Enable required addons
microk8s enable dns storage

# Deploy (script auto-detects your node IP)
chmod +x deploy.sh && bash deploy.sh

# Get your bootstrap address
NODE_IP=$(microk8s kubectl get nodes \
  -o jsonpath='{.items[0].status.addresses[?(@.type=="InternalIP")].address}')
echo "Bootstrap: $NODE_IP:30092"

Key manifest snippet — two-listener pattern

yaml
env:
  # Both listeners defined — internal (pod DNS) + external (NodePort)
  - name: KAFKA_LISTENERS
    value: "INTERNAL://0.0.0.0:9092,CONTROLLER://0.0.0.0:9093,EXTERNAL://0.0.0.0:9094"

  - name: KAFKA_ADVERTISED_LISTENERS
    value: "INTERNAL://kafka-headless.kafka.svc.cluster.local:9092,EXTERNAL://NODE_IP:30092"

  - name: KAFKA_PROCESS_ROLES
    value: "broker,controller"   # KRaft combined mode — no ZooKeeper
Why two listeners?

Kafka clients connect directly to brokers after bootstrapping. The EXTERNAL advertised listener must be your actual laptop-reachable node IP, not a Kubernetes DNS name. The INTERNAL listener handles pod-to-pod traffic inside the cluster using stable Kubernetes DNS.

KEDA Consumer Autoscaling

KEDA watches Kafka consumer lag and automatically scales your consumer Deployment up or down.

lag > 5000
→
KEDA detects
→
scale replicas up
lag < 1000
→
cooldown 30s
→
scale replicas down

Scaling formula

formula
desiredReplicas = ceil( totalLag / lagThreshold )
               = ceil( 15000   / 5000          )
               = 3  (capped at maxReplicaCount)

ScaledObject

yaml
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: rollup-consumer-scaler
  namespace: kafka
spec:
  scaleTargetRef:
    name: rollup-consumer
  minReplicaCount: 1     # always keep 1 alive
  maxReplicaCount: 3     # cap = partition count
  cooldownPeriod:  30    # seconds before scale-down
  pollingInterval: 5     # check lag every 5s
  triggers:
    - type: kafka
      metadata:
        bootstrapServers: "kafka-headless.kafka.svc.cluster.local:9092"
        consumerGroup:   "rollup-worker"
        topic:           "metrics.raw"
        lagThreshold:    "5000"

Local Stack Manager

Save replica counts for any namespace, scale everything to 0 to free RAM, restore exactly later. State stored in ~/.k8s-stacks/<namespace>.env.

bash — daily workflow
# Install once
sudo cp k8s-stack.sh /usr/local/bin/k8s-stack
chmod +x /usr/local/bin/k8s-stack

# Evening — free up RAM
k8s-stack down kafka
k8s-stack down monitoring

# Morning — restore
k8s-stack up kafka
k8s-stack up monitoring

# Or all stacks at once
k8s-stack down --all
k8s-stack up   --all

# See what's running vs saved
k8s-stack status kafka
k8s-stack list

State file format

~/.k8s-stacks/kafka.env
# k8s-stack state for namespace: kafka
# saved at: 2024-03-14 10:30:00
NAMESPACE=kafka

# Deployments
rollup-consumer=3

# StatefulSets (prefixed with sts:)
sts:kafka=1

You can edit this file directly — change rollup-consumer=3 to rollup-consumer=1 if you want it to start with fewer replicas next time.

Quick Reference

System Design Cheatsheet

DecisionRule
Partition keyHigh cardinality entity id. Stateful aggregation → metric/group key. No ordering needed → null (round-robin).
Partition countmax(throughput÷broker_ceiling, ingest_rate÷consumer_capacity) × headroom. Round up to power of 2.
Replication factorAlways 3 in production. Never 1. Pair with min.insync.replicas=2.
Consumer scalingLag growing → add consumers (up to partition count). New use case → add new group.
RetentionPipeline=short (days). Replay=long (weeks). State sync=compaction. Audit=long no-compaction.
Offset commitAlways manual. Commit after successful processing. Never auto-commit.
Delivery semanticsDesign consumers idempotent regardless. At-least-once is default and safe when idempotent.
Max partitions/broker4,000. Beyond this: controller elections slow, rebalances degrade.

microk8s kubectl exec -n kafka kafka-0 -- \
  /opt/kafka/bin/kafka-consumer-groups.sh \

  /opt/kafka/bin/kafka-console-consumer.sh \
    --bootstrap-server localhost:9092 \
